# Microsoft 365 outage, November 12 to 13, 2026: what is known

!!! info "Research notes, not workbook guidance"
    **Status:** Open · **Last checked:** 2026-11-13 · **Baseline:** Microsoft 365 GCC Moderate

**Question:** was the Microsoft 365 outage of November 12 and 13, 2026 a denial-of-service
attack? What happened, when, which services were hit, what does a GCC Moderate tenant need to
check, and does the workbook's notice handling catch an incident like it?

**Short answer, so far:** Microsoft says no. Its status page calls it "a technical issue not
related to cyber or AI / agents", introduced during an earlier network capacity upgrade and
surfacing after a recent network change. Microsoft hasn't published its post-incident report
yet. This page stays **Open** until it does.

Sources are marked by type: **[Microsoft status]** for Microsoft's public status page and its
@MSFT365Status account, **[Learn]**, **[CISA]**, and **[Non-Microsoft]** for news and security
coverage. Times are UTC. Where a news report gave a local time, it is converted and marked as
the outlet's time. Facts and claims are kept apart: anything Microsoft hasn't confirmed is
labeled as a claim.

The finished guidance on provider notices lives in the
[Federal Modernization Workbook](https://whalermike.github.io/modernization-workbook/). Nothing
here changes it.

## What Microsoft has said

From Microsoft's public status page, read through its JSON feed (`/api/posts/mac`) on
2026-11-13 **[Microsoft status]**:

- **Title:** "Users may be unable to connect to multiple Microsoft 365 services". **Status:**
  Service degradation, both at 16:07 and at 17:57 UTC on November 13.
- **16:07 UTC update:** "no evidence of malicious activity". It promised a full post-incident
  report with root cause and defense-in-depth actions after mitigation.
- **17:57 UTC update:** "broad recovery and stability". The cause was "a technical issue not
  related to cyber or AI / agents". The incident "was introduced by an issue during an earlier
  network capacity upgrade" and surfaced after a recent network change. Microsoft says it has
  addressed the underlying issue and restored services gradually, checking stability at each
  stage. A full post-incident report will follow its review. Next update by 20:00 UTC.
- **Azure:** "No Azure issues detected at this time" at 16:15 and at 18:52 UTC.

The public page doesn't show incident IDs. It says it exists for administrators who "may be
unable to access the admin center".

## Services affected

The status page lists features of Microsoft 365 services that depend on Exchange Online
**[Microsoft status]**:

- Exchange Online, through Outlook on the web, Outlook desktop, Exchange ActiveSync and REST;
  email delivery delayed
- some pages of the Microsoft 365 admin center, and the Microsoft 365 Apps admin center
- Microsoft 365 Copilot
- Defender XDR portal pages, and Defender for Office 365 features that use Purview signals
- Microsoft Graph calls that read mail, calendar or contacts
- Intune enrollment, check-in and compliance (intermittent)
- Purview: DLP, labeling, audit search and eDiscovery
- Teams: calendar, scheduling and meeting features (calls, chats and channel messages kept
  working)
- SharePoint external sharing
- Planner, To Do, Power Apps mobile sign-in, Power BI and Fabric label exports, Universal Print,
  and Windows 365 with Purview Customer Key

## GCC Moderate

**Not stated.** Neither Microsoft's public page nor any news report read here mentions GCC.
Treat a GCC Moderate tenant as possibly affected until its own Service health says otherwise.

## Was it a denial-of-service attack?

- **Microsoft's position:** no. The load didn't come from more traffic; it found no evidence of
  malicious activity; and on November 13 it said the cause was "not related to cyber"
  **[Microsoft status]**.
- **Claims:** a threat-intelligence account on X reported that a hacktivist group published
  material about Outlook's availability on November 12. **Unverified.** The same post says the
  evidence doesn't confirm the group caused anything. Euronews reports no group claimed
  responsibility **[Non-Microsoft]**.
- **Speculation:** some security blogs still list a DDoS as a hypothesis. Nothing Microsoft has
  published supports it.
- **Azure Front Door or Azure network:** no Azure incident found. Azure's status was Available,
  and Azure's status history has no post-incident review dated November 11 to 13
  **[Microsoft status]**.

## What a tenant administrator can check

These checks need an admin sign-in, so they happen at work, not here:

- In the Microsoft 365 admin center, open **Health > Service health**. Look for **EX1550543**,
  **MO1550821** and **TM1550488**, and record whether each one appears for the tenant and when it
  started. If the admin center doesn't load, use the public status page. **[Learn]** names that
  page for exactly this case.
- On an open issue, **Manage notifications for this issue** sends each update to up to two email
  addresses per admin **[Learn]**.
- When the issue's status changes to **Post-incident report published**, download the report
  from Service health **[Learn]**. File it with the incident timeline and the service desk's
  ticket count.

## What the workbook says, and the gaps

Read from the workbook's `origin/main` on 2026-11-13 (commit `e115f824`).

- **The provider-notices kit routed a Microsoft 365 incident to the weekly digest only.** Its
  routing template's open-incident rule needs the provider to name the agency's resources.
  Microsoft 365 service health issues are tenant-wide and carry no resource list, so the rule
  never matched them. On Mike's go-ahead on November 13, the kit fix goes to the workbook as its
  own change. It doesn't cite this incident.
- **Nothing alerts on Microsoft 365 as it happens.** Gate 1 of the
  [provider notices guide](https://whalermike.github.io/modernization-workbook/docs/books/guides/provider-notices-implementation.html)
  sets up Azure Service Health alerts. Microsoft 365 has no equivalent step, such as the Service
  health email preference.
- **No page names the fallback channels:** the public status page, @MSFT365Status, and Service
  health email.
- **[Book 15](https://whalermike.github.io/modernization-workbook/docs/books/b15-day2-operations/14-provider-notices.html)
  says, correctly, that the weekly read isn't for detecting incidents.** But its recovery
  runbooks cover identity and devices only; none covers "a provider's SaaS service is down".
- **Not gaps:** the Azure Security guide's DDoS step and Book 10's ingress section protect the
  agency's own Azure public endpoints. They don't apply to an outage on Microsoft's side.

## What could move to the workbook

These items wait for Microsoft's post-incident report and for Mike's named approval:

1. A Gate 2 note on the fallback channels and the Service health email preference, cited to
   Learn.
2. A "provider SaaS outage" runbook in Book 15, Appendix B.
3. A Microsoft 365 telemetry line in Book 12, Chapter 04.

The incident itself would be cited only through Microsoft's own post-incident report.

## Open questions

- Microsoft's root cause and its defense-in-depth actions (wait for the post-incident report).
- Whether GCC tenants were affected (check Service health at work).
- Whether TM1550488 was related.
- Whether the earlier description, a process that sets up secure connections becoming
  overwhelmed, and the patch to the authentication and routing component match the network
  capacity upgrade cause Microsoft gave on November 13.
